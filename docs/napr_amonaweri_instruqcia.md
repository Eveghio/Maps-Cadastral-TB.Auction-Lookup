# საჯარო რეესტრი: საკადასტრო კოდიდან ამონაწერის და საკადასტრო გეგმის (PDF) პოვნა

ტექნიკური ინსტრუქცია ექსთენშენის, სკრიპტის ან პროგრამის ასაწყობად.
შემოწმებულია ცოცხლად, 2026 წლის 12–13 ნოემბერს, რეალურ გვერდებსა და ~150 PDF-ზე (2007–2026).

**ვერსია 4.** საცნობარო კოდი ცალკე ფაილშია: **`napr_docs.js`** (ES module, გარე ბიბლიოთეკის გარეშე). მასში გაერთიანებულია მეორე ჩატის `plan_reader.mjs` (გეგმის ამოცნობა, დაშიფრული ასლები) და ამ ინსტრუქციის გასწორებები (ნაწ. 4). ინსტრუქციის ნაწ. 4–7 ამ ფაილს აღწერს.

## 1. რას აკეთებს

შემავალი მონაცემი არის საკადასტრო კოდი, მაგ. `01.10.14.028.016`, `01.01.834` (ხაზობრივი ნაგებობა) ან `01.16.03.058.081.01.01.009ა` (ბინა). შედეგი არის PDF-ის პირდაპირი ლინკი:

- **ამონაწერი:** ქრონოლოგიურად ბოლო, ან N-ე ბოლოდან;
- **საკადასტრო გეგმა:** ნამდვილი გეგმა და არა სიაში "საკადასტრო რუკად" მონიშნული სიტუაციური ან აზომვითი ნახაზი.

ორივე ერთი და იმავე გვერდიდან იწყება (ნაწ. 2–3). სწორი არჩევანისთვის PDF-ის შიგთავსის წაკითხვა სჭირდება (ნაწ. 4–6).

## 2. წყარო: ამონაწერების გვერდი

```
GET https://abstract.reestri.gov.ge/abstract/cad_amo.php?cad_code=<საკადასტრო კოდი>
```

HTML, UTF-8, ავტორიზაციის გარეშე. კოდი URL-encode-ით გადაეცი (`encodeURIComponent`). ბრაუზერში გვერდის სათაურია "არსებული დოკუმენტები".

**კოდის ამოცნობა ტექსტიდან** (მონიშნული ან დაკოპირებული):

```
(?<![\d.])\d{1,2}(?:\.\d{1,3}){2,9}[\u10D0-\u10F0]?(?![\d.])
```

| კოდი | მაგალითი | გვერდზე შემოწმებულია |
|---|---|---|
| 3 ნაწილი (ხაზობრივი ნაგებობა) | `01.01.834` | ✓ (93 დოკუმენტი) |
| 4 ნაწილი (რეგიონები) | `04.01.12.277` | ✓ |
| 5 ნაწილი (მიწა, თბილისი) | `01.10.14.028.016` | ✓ |
| გრძელი (ბინა / ნაწილი) | `01.16.03.058.081.01.01.009` | ✓ |
| ბოლოში მიბმული ქართული ასო (ბინა) | `01.16.03.058.081.01.01.009ა` | ✓ (ცალკე დოკუმენტები აქვს, ასოს გარეშე კოდისგან განსხვავებით) |

- ასო **კოდის ნაწილია**: `…009ა` და `…009` სხვადასხვა ობიექტია, ამიტომ ასო არ მოაშორო. URL-ში `encodeURIComponent`-ით გადადის.
- `(?<![\d.])…(?![\d.])` თარიღებს გამორიცხავს: `12.05.2024`-ს კოდად არ ცნობს. თუმცა 2-ნიშნა წლიანი თარიღი (`12.05.24`) სამნაწილიან კოდს ჰგავს და დაემთხვევა. თუ ეს პრობლემაა, სამნაწილიანი კოდი მხოლოდ მაშინ მიიღე, თუ ტექსტში სხვა კოდი არ არის.

## 3. გვერდის აგებულება

თითო PDF ერთი `<tr>` სტრიქონია. **ლინკი სტრიქონის `onclick` ატრიბუტშია**, არა უჯრაში ან `<a>` ტეგში:

```html
<tr onmousemove="move1(this.id)" onmouseout="move2(this.id)"
    onclick="openWindow('https://bs.napr.gov.ge/GetBlob?pid=101&bid=XXXXXXXX');"
    id="37712787" height="25" class="style1">
  <td>&nbsp;რეგისტრაციის ნომერი:&nbsp;882026579733</td>
  <td>&nbsp;რეგისტრაციის თარიღი:&nbsp;01/07/2026</td>
  <td>&nbsp;განაცხადის ნომერი:&nbsp;35180140</td>
  <td>&nbsp;ამონაწერი&nbsp;</td>
</tr>
```

| უჯრა | შიგთავსი |
|---|---|
| 1 | რეგისტრაციის ნომერი, ანუ **განცხადების** რეგისტრაციის ნომერი |
| 2 | რეგისტრაციის თარიღი (დდ/თთ/წწწწ), ანუ **განცხადების შეტანის** დღე |
| 3 | განაცხადის ნომერი |
| 4 | ტიპი: `ამონაწერი` ან `საკადასტრო რუკა` |

**რაც უნდა გაითვალისწინო:**

1. **სიის რიგი განცხადების შეტანის თარიღით არის დალაგებული, უახლესი ზემოთ. დოკუმენტის მომზადების დროს არ ითვალისწინებს.** სიაში მოცემული თარიღი განცხადების დღეა და არა ამონაწერის. ერთ მაგალითში განცხადება 01/07/2026-ს შევიდა, ამონაწერი კი 07/08/2026-ს მომზადდა. ამიტომ "სიაში პირველი" ყოველთვის ქრონოლოგიურად ბოლო არ არის (იხ. ნაწ. 5).
2. **"დუბლიკატები" ცალ-ცალკე ფაილებია.** ერთი და იგივე განცხადების ორი სტრიქონი ორ განსხვავებულ ლინკს შეიცავს: ერთი PDF ელექტრონულად **ხელმოწერილია**, მეორე **ხელმოუწერელი** ან დაშიფრული. შიგთავსი ერთია. რომელი წყვილის რომელ სტრიქონშია, არ არის მუდმივი.
3. **ერთ განცხადებაზე** შეიძლება რამდენიმე სხვადასხვა "საკადასტრო რუკა" იყოს, მაგ. ნახაზი და გეგმა.
4. **"საკადასტრო რუკა" ყოველთვის საკადასტრო გეგმა არ არის.** იმავე ტიპით იწერება სიტუაციური ნახაზი, აზომვითი ნახაზი და სხვა ატვირთული ნახაზები (იხ. ნაწ. 6).
5. **უჯრების ტექსტში არის `&nbsp;`.** შედარებამდე trim და whitespace-ის ნორმალიზაცია გააკეთე.
6. **არარსებული კოდი:** გვერდი იტვირთება, მაგრამ `<tr>` სტრიქონები არ აქვს. `openWindow` ტექსტი მაინც ჩანს script-ში. **ამიტომ ლინკი მხოლოდ `<tr ... onclick=...>`-დან ამოიღე.**
7. **HTML entity-ები** ყოველთვის გაშიფრე (`&amp;` → `&`).

## 4. PDF-ის წაკითხვა: რა არის შიგნით

PDF-ები `https://bs.napr.gov.ge/GetBlob?...`-დან ავტორიზაციის გარეშე ჩამოიტვირთება (GET, 30 KB–4 MB). ტექსტის ამოსაღებად გარე ბიბლიოთეკა საჭირო არ არის: შეკუმშული ნაკადები `DecompressionStream("deflate")`-ით იხსნება, ქართული ტექსტი ფონტების `ToUnicode` / `/Differences` ცხრილებით იშიფრება, დაშიფრული ასლები MD5 + RC4-ით (კოდშივე). იხ. `napr_docs.js` → `pdfText`, `describeDoc`.

**რაც PDF-ებში დადასტურდა:**

| დოკუმენტი | რა იკითხება |
|---|---|
| ამონაწერი, 2024–2026 | ქართული ტექსტი; `განცხადების … N <ნომერი> - <შეტანის დრო> <მომზადების დრო>` |
| ამონაწერი, 2012–2024 | ქართული ძველი 8-ბიტიანი კოდირებითაა, მაგრამ **ნომერი და ორივე თარიღი იკითხება** |
| ამონაწერი, 2007 (2008–2011 არ შემოწმებულა) | ფორმატი არ ამოიცნობა; დრო მხოლოდ `/CreationDate`-იდან |
| **ამონაწერის / გეგმის დაშიფრული ასლი** | **იკითხება** (RC4 128, ცარიელი პაროლი; შემოწმდა 2012–2026 ამონაწერებზე და 2016–2021 გეგმებზე). AES (V4+) ფაილი არ შეგვხვედრია; ასეთზე `encrypted-unsupported` |
| საკადასტრო გეგმა, 2016-დან | ქართულად `საკადასტრო გეგმა` + `მომზადების თარიღი: dd/mm/yyyy` (დროის გარეშე) |
| საკადასტრო გეგმა, 2016-მდე | ლათინურად (AcadNusx) `sakadastro gegma` (ArcMap: WinAnsi ფონტი; Ghostscript: `/Differences` ფონტი). თარიღი `/CreationDate`-იდან |
| სიტუაციური ნახაზი | `situaciuri naxazi` / `სიტუაციური ნახაზი` |
| აზომვითი ნახაზი | რეესტრის სიის ფაილებში ეს ფრაზა **მხოლოდ შტამპში** შეგვხვდა: „…აზომვითი ნახაზი არ შეესაბამება №315/№388…“. შტამპი ტიპი არ არის: ჯერ ამოიჭრება |
| ნახაზი, სადაც ტექსტი მრუდებადაა | ტექსტი არ იკითხება → `unknown` |

**მომზადების დრო (ამონაწერი):**

```
N\s*(\d{9,})\s*-\s*(\d{2}/\d{2}/\d{4}\s+\d{2}:\d{2}:\d{2})\D{0,20}?(\d{2}/\d{2}/\d{4}\s+\d{2}:\d{2}:\d{2})
   ჯგუფი 1 = განცხადების ნომერი, 2 = შეტანის დრო, 3 = მომზადების დრო
```

სარეზერვო წყარო: `/CreationDate` (ხელმოუწერელ ასლში მომზადების დროს ემთხვევა; დაშიფრულ ასლში ჯერ გაშიფვრა სჭირდება).

**PDF-ის წამკითხავის ხაფანგები** (ცოცხალ ფაილებზე ნაპოვნი; `napr_docs.js`-ში გათვალისწინებულია):

1. **ნაკადის ბოლოს `\r\n`**, `endstream`-მდე. `DecompressionStream` ამას შეცდომად თვლის და **ბოლო ნაწილს აგდებს** (461 KB-დან მხოლოდ 128 KB რჩებოდა, ამიტომ ხელმოწერილი გეგმა „unknown“ გამოდიოდა). გამოსავალი: პირდაპირი `/Length` და, შეცდომისას, 1–2 ბაიტით მოკლე ცდა.
2. **ხელმოწერილ ფაილებში ციფრების გრძელი მწკრივები** (86 000 სიმბოლო). ობიექტების ძებნის regex `(\d+)\s+(\d+)\s+obj` მათზე კვადრატულად ნელდება: 1.5 წმ ერთ ფაილზე. გამოსავალი: `(?<!\d)(\d+)\s+(\d+)\s+obj`, რაც 1 მწმ-ს ხარჯავს.
3. **ერთი ფონტის სახელი (`/F0`) სხვადასხვა გვერდზე და ხელმოწერის ბლოკში სხვადასხვა ფონტია.** ფონტი ყოველი გვერდის ან ფორმის საკუთარი `/Resources`-იდან უნდა ამოიკითხო (საჭიროებისას `/Parent`-იდანაც). ერთიანი ცხრილი ტექსტს აფუჭებს.
4. **დაშიფვრის გასაღებისთვის საჭირო `/ID` ზოგ ფაილში ჩვეულებრივი სტრიქონია, `(...)`, და არა `<hex>`.** ამის გამო დაშიფრული ამონაწერები არ იკითხებოდა. ასევე `/O (` ჰარით.
5. **ფონტები ფაილის მიხედვით განსხვავდება:** ToUnicode → `/Differences` (glyph-სახელები) → Latin-1, თითო ფონტზე ცალკე.
6. **სიჩქარე:** სურათები, ფონტის ფაილები (`/FontFile*`), XMP და xref ნაკადები არ იხსნება.
7. **ინლაინ სურათები** (`BI … ID … EI`) კონტენტ-ნაკადიდან ამოიჭრება, რადგან ბინარში შემთხვევითი `(` ტექსტის ამოღებას ჭრის.
8. **ბრაუზერის `TextDecoder("latin1")` სინამდვილეში windows-1252-ია:** ბაიტებს 0x80–0x9F-ში ცვლის. ბაიტ-ზუსტი სტრიქონისთვის `String.fromCharCode` გამოიყენე.

## 5. ალგორითმი: ამონაწერი (ბოლო ან N-ე)

```
1. წაიკითხე გვერდი (ნაწ. 2) და აიღე type == "ამონაწერი" სტრიქონები, სიის რიგით
2. ჩამოტვირთე PDF-ები (ერთდროულად 4; მეტი რეესტრის სერვერს ანელებს) და თითოეულიდან ამოიღე:
     prepared = მომზადების დრო (ტექსტიდან; თუ არა, /CreationDate)
     signed   = PDF-ში არის /ByteRange
3. დააჯგუფე ერთი დოკუმენტის ასლები: იგივე რეგისტრაციის ნომერი (სიის 1-ლი უჯრა) და დრო ±15 წთ
     ჯგუფში ინახე ყველა ლინკი; გასახსნელად აირჩიე ხელმოწერილი
4. დაალაგე ჯგუფები prepared-ით კლებადობით. თუ prepared და /CreationDate ორივე უცნობია, გამოიყენე სიის თარიღი.
```

## 7. საცნობარო კოდი: `napr_docs.js`

ფაილი ES module-ია და მუშაობს ექსთენშენის გვერდზე, service worker-ში (`"type": "module"`) და Node 18+-ზე. გარე ბიბლიოთეკა არ სჭირდება.

| ექსპორტი | რას აკეთებს |
|---|---|
| `findDocuments(code, "plan" \| "extract", { n, parallel })` | **ერთი გამოძახებით:** `{ status, doc, bytes, url, numbered[], other[], pageUrl }`. `doc` არის N-ე ჯგუფი (1 = ბოლო), `bytes` მისი PDF (ხელმოწერილი, თუ არის) |
| `readList(code)` / `parseAbstractPage(html)` | სიის სტრიქონები: `{ url, type, listDate, regNo, appNo, row }` |
| `describeDoc(bytes, row)` | `{ kind, prepared, preparedHasTime, created, appNo, signed, encrypted, stamp, readable }` |
| `groupDocs(docs)` | ასლების დაჯგუფება და დალაგება (ნაწ. 5–6). ჯგუფი: `{ kind, when, prepared, rows[], best, signedRow, appNo, stamp }` |
| `pdfText(bytes)` | PDF-ის ტექსტი: `{ text, created, signed, encrypted }` |

```js
import { findDocuments } from "./napr_docs.js";

const plan = await findDocuments("01.10.14.028.016", "plan");          // ბოლო საკადასტრო გეგმა
if (plan.status === "found") save(plan.bytes);                         // PDF -> მაგ. KML-ად კონვერტაცია
console.log(plan.other.map((g) => g.kind));                            // სიაში არსებული ნახაზები

const ex2 = await findDocuments("01.14.11.016.020", "extract", { n: 2 }); // წინა ამონაწერი
console.log(ex2.doc.when, ex2.url);
```

მეორე ჩატის `plan_reader.mjs`-თან შედარებით `describeDoc` იგივე წესით ცნობს გეგმებს. დამატებით გასწორებულია ნაწ. 4-ის ხაფანგები 1–4 და 6, ასევე ძველი განცხადების ნომრები (`012007…`): ისინი სიის სტრიქონიდან აიღება.
